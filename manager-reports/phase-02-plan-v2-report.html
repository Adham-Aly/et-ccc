01

What changed from v1

v1 was rejected for misreading the product: an interactive judge, not a reading app, and far too large to run. Six changes answer that directly.

1

Reading only

Pyodide, the in-browser runner, the editor, exercises and grading are gone. Code in lessons is read-only, with a copy button.

2

Vercel, not local

A plain Next.js app, every page built ahead of time. No backend, no database, no server code to run or secure.

3

Practice via links

WMOJ for 2021–2026, DMOJ for 2020 and earlier, WMOJ preferred. No problems live inside the app itself.

4

Private GitHub repo

Created with the existing gh login. Nothing changes globally on the Mac; not yet executed — waits on P3.

5

Far fewer agents

41 spawns over 7 phases, at most 3 workers at once, versus about 294 over 16 phases in v1.

6

New: real visuals

Extensive animated step-throughs and code traces, added mid-redo on your instruction (D-021).

On visuals: every animation replays a trace recorded by running the real Python once while the lesson is written. Nothing executes in the learner's browser, so the no-code-execution rule still holds.

02

The app in a few lines

A free, Python-only course that takes a complete beginner to CCC Senior level, built as static pages and served from Vercel. Lessons explain, show read-only code, and animate what is happening. To practice, the page links out to the real judge.

Agent orchestration, in practice

This is the section that matters most for how the build actually runs day to day.

The hierarchy
Main session (tier 0)
Talks to you, launches one phase orchestrator at a time, launches the Manager report after each phase
↓ launches, one phase at a time
Phase orchestrator (tier 1)
Opus or Sonnet, per phase · plans the phase, dispatches workers, integrates their output
↓ dispatches, at most 3 at once
Workers (tier 2)
Authors, reviewers, engineers · write results to files · never spawn subagents
No sub-orchestrators, no swarms, no Workflow tool. Main → orchestrator → workers is the only shape used.

41 spawns (19 Opus, 22 Sonnet), cap 48, over 7 phases, at most 3 concurrent. About 7× fewer. The savings: no runtime/exercise phases, content in 3 phases instead of 8, one reviewer per phase instead of per-batch verifiers, contiguous module runs per author, and Sonnet for Stages 0–4.

How context moves between phases
  • Nothing important travels only in a message. Every agent writes results to files first and returns a short pointer to them.
  • progress.md holds phase status and worker checklists; it's the first thing any agent reads on a cold start.
  • decisions.md is an append-only log of every ruling, including yours.
  • Each phase closes with phase-logs/phase-NN-*.md, which the next phase reads first.
  • Content status lives in each module's own file (planned → drafted → gated → reviewed → accepted), rebuilt into a ledger on demand, never hand-edited.
On interruption or redo
  • Interrupted: the next agent reads progress.md, finds the phase marked in progress, and resumes from the first unfinished item. If a worker's process is gone, one same-role, same-model replacement is spawned with the same files and instructions; that counts against the phase's spawn cap.
  • Redo: the old phase log is archived as .v<k>, superseded files move aside, your critique is logged, and the new run must address it explicitly in its own log. This report is itself the product of exactly that process, following your critique of v1.

05

Decisions waiting on you

Beyond approving the plan itself, 13 open questions are waiting, grouped by the phase each one blocks. Each has a recommendation; a default is used only where the plan says work may continue on it.

Needed before P3
Q-17Repo name, commit identity, and a standing commit instruction?

Recommend: name it et-ccc (private), use your existing git identity, and auto-commit & push each phase branch at phase end, merging to main only after you approve.

Tradeoff: saves back-and-forth, but work lands in git before you've reviewed it — merges to main still wait for your OK.

Q-13Some traces land outside the workspace no matter what — acceptable?

Recommend: acknowledge Playwright's browser cache, Claude Code's own session files, and reading your existing gh login as system- or harness-owned, and keep them listed openly.

Tradeoff: total containment of installed tooling stays intact; only pre-existing system housekeeping we don't control isn't.

Q-14Can we fix the process files, which are already out of date?

Recommend: yes — the main session updates operating-rules.md, 00-START-HERE.md and project-brief.md right after you approve the plan.

Tradeoff: keeps the process docs accurate; a small edit outside any phase's normal remit.

Q-15Should the writing-style checker run on the project's own Node instead of the Mac's system Node?

Recommend: yes — it's patched and matches the Node version Vercel builds with.

Tradeoff: none real; keeps containment total.

Needed before P4
Q-18Which Vercel account, and should previews stay password-protected?

Recommend: your personal account, Hobby plan; keep previews protected with a bypass secret for automated tests; production stays public.

Tradeoff: protected previews hide drafts from outsiders, but need a bypass secret wired into test tooling — if your plan lacks that, we test against production after each merge instead.

Q-21Should learners be able to edit a visual's input, not just step through presets?

Recommend: not in v2 — each visual ships 2–3 authored presets recorded from the real Python.

Tradeoff: custom inputs would need a second, browser-side copy of every algorithm, which reopens the no-code-execution rule and doubles the correctness burden.

Needed before P5
Q-19What device and OS will the learner actually use?

Recommend: tell us macOS, Windows or ChromeOS; default plan assumes a laptop with a bundled-Python editor (for example Thonny), with PyPy 3.8 added at Stage 2.

Tradeoff: a wrong guess means the setup lesson doesn't match the real device — cheap to fix now, awkward once content is written.

Q-20How much full solution content should lessons include?

Recommend: about 50–70 key CCC problems get full in-lesson walkthroughs, plus a short optional hint on every practice link; no dedicated page per problem.

Tradeoff: keeps writing effort bounded; a full editorial page per problem stays possible later, as its own phase.

Q-2Can lessons mention a problem's own subtask breakdown when teaching partial marks?

Recommend: yes, as a fact about one specific problem, never as a target or cutoff.

Tradeoff: a genuinely useful teaching detail, without reopening the no-score-targets rule.

Q-4Who writes the hand-written teaching-voice sample?

Recommend: you write about 400–600 words, or substantially rewrite a draft we provide.

Tradeoff: a genuine sample gives the style checker a real target; skipping it risks the whole course reading synthetic.

Q-7Can we use older CCC years on DMOJ where no 2014–2026 problem fits a technique?

Recommend: yes, still CCC, same link rule, added to the registry with verification. No non-CCC problems.

Tradeoff: fills real gaps (for example lazy propagation, LCA) without loosening what counts as practice.

Q-10Drop module M7.14, the "C++ bridge"?

Recommend: yes — it conflicts with the Python-only rule and the no-comparison-framing rule.

Tradeoff: none; module count lands exactly at 105 either way.

Needed before P10
Q-9Once CCC 2027 problems exist, do they go to WMOJ like 2021–2026?

Recommend: almost certainly yes; decide when they actually appear. Until then the build refuses years after 2026 rather than guessing.

Tradeoff: no action needed before P10; flagged now so it isn't forgotten.
