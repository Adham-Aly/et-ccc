01

What the app is

A free website that takes one learner from never having written code to solving CCC Senior problems S1 to S5 in Python. It is built for the specific learner you have in mind, working alone at their own pace.

There are no accounts and no server. The pages, the Python that runs the learner's code, and their saved progress all live in their web browser. When the learner wants to test a solution at real contest speed, the app links out to two free online judges, WMOJ and DMOJ.

  • Light mode only, in the app and in these reports.
  • Python only, written for Python 3.8, the version the contest grader runs.
  • No score targets. This is a hard rule: the app never mentions target scores, cutoffs, expected results, or claims that Python “can't” solve something. It stays about learning.
  • Problem statements are paraphrased, never copied, and every problem page credits the CEMC. The app is free and non-commercial, as the CEMC licence requires.

The learner's experience

A typical session: open the home page, follow the suggested next step, work through a lesson, and clear a few review items.

Home: “Recommended next”→ Lesson with exercises→ Module checkpoint→ Practice problems→ Today's review

The home page shows the recommended next step, how many review items are due today, recent activity, and a reminder to back up progress. It shows no scores.

A lesson

Lessons change shape as the learner grows. Early on they move in very small steps with a lot of support. Later the support fades and lessons start from a real contest problem.

Every new term is defined where it first appears and collected in a glossary. Diagrams of grids, graphs, trees and tables are drawn by hand for the course, and some can be stepped through one move at a time.

How it works

  • Run tries the code on the learner's own input. Submit grades it against the tests.
  • Results use the contest grader's own words: Correct, Wrong Answer, Time Limit Exceeded, Run-time Error.
  • A program stuck in a loop is stopped at the time limit and a fresh Python is ready at once, so there is no waiting.
  • The first visit downloads the Python engine once (about 6 MB).

Made for beginners

  • An error explainer turns common errors into plain language with a link to the right lesson.
  • The editor flags Python features newer than 3.8 as you type. They block Submit but never Run.
  • A warning appears if the code prints a prompt like input("Enter:"), a classic way to fail on the real grader.
  • Honest about speed: time limits adjust for slow devices, and real timing is checked on the judge.

Progress, review and practice tools

Completion and mastery

  • A module is complete when its lessons are done and its checkpoint is passed: 6 to 12 mixed questions, mostly on this module and some on earlier ones. Two tries each.
  • A failed checkpoint points to the exact lessons to revisit and offers a retake with fresh questions.
  • Mastered means the checkpoint was passed without hints and a review a week or more later was passed too. It shows as a quiet badge, never a percentage.

Guided, never locked

  • A “Recommended next” path is always shown.
  • If a lesson needs something not yet finished, a banner says so and offers a link or “continue anyway”.
  • A confident learner can skip ahead by taking a checkpoint cold.

Spaced review

Items come back at growing gaps, measured in days after learning, up to 10 a day. A correct answer moves an item to the next gap. A problem solved with the walkthrough open returns after a week as “solve from scratch”.

1 3 7 16 35 days

Template drills

16 standard algorithms typed from memory in a blank editor, because the contest bans prewritten code. Shows personal best and trend, with no time goals.

Mock contests

26 past papers (13 Junior, 13 Senior) with a 3-hour timer and grader-style feedback per subtask, if you allow it (Q-2).

Saving progress

Saved in the browser automatically. One-click export and import of a backup file, with a “last backup N days ago” reminder.

Other pages: a first-visit guide, the course map, a problem browser with filters, search, glossary, settings, and an about page with credits.

One principle behind the content

Nothing that can be checked is typed by hand. Judge links, expected outputs, trace tables, subtask tables and constraint numbers are all computed from data or by running the code. That removes a whole class of mistakes across roughly 490,000 words.

05

Quality checks

About 30 automatic checks guard the app and the content. A quick set runs on every change; the full set runs before a batch of content is accepted and at the end of every phase. Each check comes with a test case proving it catches what it claims to. Every phase must end with zero warnings, zero failing or flaky tests, and zero open defects.

How each piece of content moves

1AuthorAn agent writes it, then runs the quick checks until they pass.
2ChecksCode, links, style, no-score rule, Python 3.8.
3VerifierA second agent re-runs everything, writes stress tests, screenshots each page.
4CriticA third agent reads it as a beginner would and judges the teaching.
5AcceptedOnly accepted content ships.

The Python 3.8 check, in three layers

The browser runs a newer Python (3.14) than the contest grader (3.8). No working Python 3.8 exists for browsers, so three layers each catch what the others miss.

1

In the editor, as the learner types

Three checkers look for features newer than 3.8 and underline them. They block Submit but never Run, and each message links to the lesson on the 3.8 limits.

2

Inside the browser's Python

Library functions added after 3.8 are removed before the learner's code runs, so they fail the same way they would on the grader.

3

When content is written

Every piece of Python in the course is checked by the same tools, then run under real PyPy 3.8 and in browser Python. At the end of each stage and at release it also runs on the grader's exact version, PyPy 7.3.9.

App code

  • Code style and error check with zero warnings.
  • Type checks and unit tests for every core piece: links, grading, saving, review schedule, search.
  • Scripted walkthroughs of the real app in the Chrome, Firefox and Safari engines: running code, grading, timeouts, hints, backups, and “no request leaves the site”.

Pixel-level UI

  • Screenshots of every page type and key state at 3 screen sizes, compared with approved ones. At most 50 pixels may differ.
  • Changing an approved screenshot needs a written visual review by an Opus agent.
  • Accessibility (WCAG 2.2 AA) with zero violations, and no sideways scrolling at phone width, on every page.
  • No dark styles anywhere. Page speed budgets.

Content correctness

  • Every reference solution passes all its tests.
  • Deliberately wrong “decoy” solutions must fail the right tests, which proves the tests have teeth.
  • Slow approaches must actually time out, and correct ones must run in under a second.
  • Lessons only use ideas already taught, and course order has no loops.

Writing style

  • The avoid-ai-writing detector scans all prose, buttons and error messages.
  • Its limits are set from your voice sample and the three approved pilot items.
  • Any rewrite is compared with the original so it cannot break code, tables, links or headings.
  • Reading level for Stages 0 to 2, and a spell check with a course dictionary.

Links

  • Every judge link follows the year rule and comes from the master problem list.
  • WMOJ is checked automatically by reading each page, because WMOJ answers “OK” even for missing problems.
  • DMOJ blocks automated checks, so you tick a checklist of about 63 links (about 10 minutes).
  • Release is blocked unless every problem link is confirmed. Rechecked after 90 days.

Rules and licence

  • No-score rule: a scan of all text for banned phrasing (targets, cutoffs, “/75”, “Python can't”), tuned so “ceiling division” still passes. Critics also read for subtler cases.
  • Copyright: any run of 12 or more words matching a CEMC statement fails, and credit must be on every problem page.

Zero flakes

  • A “flaky” test passes sometimes and fails other times. New tests run 10 times in a row (20 for the runner and screenshots) and must pass every time.
  • Bugs are first reproduced as a failing test that shows what the learner would see, then fixed.

Containment of tools

  • Everything installed lives in one hidden folder inside the workspace. Deleting the workspace removes it all.
  • Tools can only be called through wrapper scripts, and a hook blocks any command that bypasses them.
  • After every install, a before-and-after snapshot of your home folder proves nothing leaked. Any leftover named after a project tool is a hard failure.
  • A few macOS records can't be avoided; they are listed openly (Q-13).

How cost stays down without cutting quality

  • Sonnet takes the mechanical work, but only where an automatic check or an Opus reviewer looks at the result afterwards.
  • Orchestrators stay lean: workers read the big files and return ten lines or fewer.
  • Fixes go back to the same agent that wrote the item, instead of starting a new one from scratch.
  • The first item of every content phase runs alone, so problems surface before a batch runs in parallel.
  • The simplest problem pages get a sampled review (one in three), with a full review if any sample fails.
  • The pilot measures real time and cost per item, and each content phase shows you its budget before it starts.
